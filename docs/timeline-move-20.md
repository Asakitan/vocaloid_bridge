# Timeline move investigation: session 20

## Red baseline

The focused synthetic AI case `preservation.timeline_event_move_20` attempts a 500-tick insertion at tick 1000, with distinct unknown fields on each tempo and meter event. The unchanged session 19 host rejected it before mutation with `timeline event identity transaction changed the tempo or time signature map`; `artifacts/feature-acceptance-af0d8654963c/summary.json` records this red baseline and successful transport cleanup. The rebuilt host later passed the expanded case with both tempo options, multiple meter events, undo, redo, clone, reopen and source preservation in `artifacts/feature-acceptance-5b8f6372f11d/summary.json`. Generated/deleted/reused-pointer cases remain outside that positive evidence.

## Mapping boundary

The existing observer probes show retained addresses for the tested insertion and meter move, but staged edits emit no observer notifications. A full before/after address bijection plus unchanged known values therefore does not independently prove that an object was not destroyed and replaced at the same address. An independently staged candidate also has different addresses and cannot resolve that ambiguity for the real transaction. The generated-boundary deletion probe already shows candidate allocation address instability. The insertion path was implemented under the bounded evidence below; session 21 subsequently added a restricted changed-map deletion path described in `docs/timeline-delete-21.md`. The implementation does not infer ownership solely from position or pointer equality.

The installed managed `InsertSilence` implementation calls `MoveTimeSig` in descending bar order for events after the current signature, shifting by `ceil(duration / barLength)`, and calls `MoveTempo` in descending tick order for events strictly after the start when tempo inclusion is enabled. Neither managed insertion path calls event insert or remove. These wrappers pass the original event pointer to native `VIS_VSM_WIVSMSequence_moveTimeSig` / `moveTempo`; the prior private observer recorded retained event addresses and position-update notifications for the fixture. The native Move implementations remain opaque, so this is bounded evidence rather than a proof for all inputs. The implementation independently checks complete candidate and actual pre/staged/post event pointer, value and expected position maps, and migrates only unknown payloads. At the session 20 checkpoint, generated, deletion and collision cases remained guarded; session 21 implements only the explicitly described deletion cases and generated tempo boundary. Existing controller cross-project, extension-audio and archive-bearing media-update guards were not changed.
